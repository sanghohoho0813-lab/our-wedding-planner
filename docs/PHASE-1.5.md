# Phase 1.5 — 둘이 동시에 쓸 때의 안정성

새 기능은 넣지 않았다. **두 사람이 같은 순간에 같은 앱을 쓸 때 데이터가 안전한가**만 보았다.

## 어떻게 검사했나

| 검사 | 무엇을 하나 | 결과 |
|---|---|---|
| `qa/realtime.mjs` | 신랑(A) · 신부(B) 를 **별도 브라우저 컨텍스트 2개**로 띄워 같은 백엔드에 붙인다 | 27/27 |
| `qa/load.mjs` | 하객 150명 · 300명으로 채우고 검색 · 필터 · 스크롤 · 참석 변경 · 식대 계산 | 33/33 |
| `qa/flow.mjs` · `audit` · `a11y` · `crossdata` · `parse` | 기존 회귀 | 141 · 16+13 · 10 · 19 · 20 전부 통과 |

**운영 데이터와 섞이지 않게 한 방법**

- 검사는 `qa/relay.mjs`(메모리 서버)에만 붙는다. 운영 Supabase 주소로는 **실행 자체가 막힌다**
  (`localhost` 가 아니거나 주소에 `supabase` 가 들어 있으면 즉시 종료).
- 동시사용 검사와 부하 검사는 서로 다른 wedding id 를 쓴다(`1111…` / `2222…`).
- relay 는 껐다 켜면 모든 데이터가 사라진다. 디스크에 남지 않는다.
- relay 는 Supabase Realtime 과 같은 모양의 이벤트(insert/update/delete)를 보내므로,
  앱 쪽 코드는 **실제와 같은 길**을 탄다.

## 찾은 문제 → 고친 것 → 다시 검사한 결과

### 1. 내가 쓴 값이 소리 없이 덮였다

- **문제** — A 가 참석으로 바꾸고 B 가 곧바로 불참으로 바꾸면, A 화면은 아무 말 없이 불참이 됐다.
  나중 것이 이기는 규칙 자체는 맞지만, **내가 방금 쓴 게 사라진 걸 모르는 게 문제**였다.
- **원인** — 충돌 감지가 "내가 쓴 값" 을 기억해 두는데, 내 수정이 메아리로 돌아올 때
  (Supabase 는 내 쓰기도 나에게 다시 보낸다) 그 기억을 지워 버렸다. 진짜 덮어쓰기는 대개 그 **다음**에 온다.
- **고친 것** — 같은 값이 돌아오면 기억을 지우지 않는다(`src/lib/store/conflict.ts`).
  덮기 전 값도 함께 기억해 두어, 뒤늦게 도착한 옛날 사진을 충돌로 오해하지 않는다(시계가 어긋나도 흔들리지 않는 판별법).
- **다시 검사** — `내가 쓴 값이 덮이면 A 에게 알려준다` 4ms 안에 안내. **PASS**

### 2. 안내가 사람 말이 아니었다

- **문제** — `상대이 참석 여부을 'no'로 바꿨어요.` — 조사도 틀리고 값도 코드 그대로였다.
- **고친 것** — 화면에서 쓰는 이름표를 그대로 쓰고(`no` → `불참`), 한국어 조사를 붙였다
  (`josa` 에 `(으)로` 추가, `particle()` 신설).
- **다시 검사** — `지윤님이 참석 여부를 '불참'으로 바꿨어요.` **PASS**
  (되돌릴 수 있게 `[내 값으로]` 버튼이 같이 뜬다. 버전 관리는 만들지 않았다 — 두 사람이 쓰는 앱에 과하다.)

### 3. 상대가 지우는 동안 내가 고치면 조용히 사라졌다

- **문제** — B 가 고치던 할 일을 A 가 지우면, B 화면에서 그냥 없어졌다. 고친 내용도 같이.
- **고친 것** — 내가 최근에 손댄 행이 지워지면 알려준다:
  *"상호님이 방금 이 할 일을 지웠어요. 고치던 내용은 저장되지 않았어요."*
- **다시 검사** — 4ms 안에 안내, 지워진 항목이 되살아나지 않음. **PASS**

### 4. 🔴 연결이 끊기면 보던 화면이 통째로 오류 화면이 됐다 (가장 큰 문제)

- **문제** — 네트워크가 끊긴 상태에서 하객 참석 여부를 바꾸자
  화면 전체가 **"데이터를 불러오지 못했어요 / 다시 시도"** 로 바뀌었다. 명단이 통째로 사라진 것처럼 보인다.
- **원인** — 활동 기록(최근 활동) 저장이 실패하면 오류 안내와 함께 `reload()` 를 불렀고,
  끊긴 상태라 그 `reload()` 도 실패해 `status = "error"` → 앱 전체가 오류 카드로 교체됐다.
- **고친 것** (3가지)
  1. `reload()` 는 **이미 받아 둔 데이터가 있으면 절대 오류 화면으로 바꾸지 않는다.** 첫 로딩일 때만 오류 화면.
  2. 연결 문제로 실패한 저장은 화면을 건드리지 않는다(되돌리기 · 재요청 없음).
  3. 활동 기록도 보낼 편지함에 쌓았다가 연결되면 보낸다 → 끊긴 동안 한 일이 '최근 활동' 에서 비지 않는다.
- **다시 검사** — `끊겨도 보던 화면이 사라지지 않는다` **PASS**, `끊겨도 내가 고친 값이 그대로 있다` **PASS**,
  `다시 붙으면 끊긴 동안의 수정이 저장된다` 608ms **PASS**

### 5. 끊긴 걸 알 방법이 사실상 없었다

- **문제** — 연결 상태 점은 **데스크톱 화면에만** 있었다. 폰에서는 저장을 시도하기 전까지 알 수 없다.
  상대의 수정이 안 오는 건데 "상대가 아무것도 안 했나 보다" 로 오해하게 된다.
- **고친 것** — 상단에 `연결 끊김 · 다시 연결 중` 표시(`SaveIndicator`). 잠깐 끊겼다 붙는 건 흔한 일이라 **4초** 뒤에만 뜬다.
  못 보낸 수정이 있으면 그게 더 중요하므로 `저장 대기 N건 · 연결되면 자동 저장` 이 우선한다(눌러서 즉시 재시도).
- **다시 검사** — **PASS**

### 6. 🔴 저장 안 되는 수정 하나가 그 뒤의 모든 수정을 막았다

- **문제** — 보낼 편지함은 순서를 지키려고 **첫 실패에서 멈춘다.**
  그런데 제약조건 위반 · 권한 없음처럼 **다시 보내도 영원히 안 되는** 실패까지 같은 취급이라,
  그 한 건이 뒤에 쌓인 모든 수정을 영구히 막고 `저장 대기` 가 영원히 남는다. (실제로 겪은 `side='both'` 제약조건이 이 경우다.)
- **고친 것** — 실패를 두 종류로 나눈다(`src/lib/store/transient.ts`).
  - 연결 문제 → 멈추고 나중에 다시(2 → 4 → 8 … 최대 30초).
  - 고쳐야 하는 문제 → **그 건만 빼내고 계속 보낸다**, 그리고 무엇이 저장되지 않았는지 알려준다.
- **다시 검사** — `안 되는 수정 하나가 뒤의 수정까지 막지 않는다` 905ms **PASS**,
  `저장 못 한 수정이 있으면 알려준다` **PASS**, `큐가 비워진다` **PASS**

### 7. 하객 300명에서 필터가 0.5초씩 밀렸다

- **문제** — 300명 기준 검색 330ms · 필터 **579ms** · 참석 변경 410ms. 눌렀는데 반 박자 늦게 따라온다.
- **원인** — 하객 한 줄마다 framer-motion `layout` 애니메이션이 걸려 있어, 한 명만 바꿔도
  **300줄 전부의 위치를 다시 재고 다시 그렸다.**
- **고친 것** — 행을 `memo` 로 감싸고(한 명 바꿀 때 나머지는 다시 그리지 않음),
  명단이 80명을 넘으면 `layout` 애니메이션을 끈다. *부드러움보다 반응이 먼저다.*
- **다시 검사 (300명, 아이폰 폭)**

  | | 고치기 전 | 고친 뒤 |
  |---|---:|---:|
  | 검색 | 330ms | **52ms** |
  | 필터 전환 | 579ms | **218ms** |
  | 참석 변경 | 410ms | **70ms** |
  | 첫 화면 | 922ms | 841ms |
  | 최악 프레임(스크롤) | 18ms | 18ms |

## 확인만 하고 고칠 것이 없던 항목

| 확인한 것 | 결과 |
|---|---|
| A 가 할 일을 고치면 B 화면에 반영 | 3–7ms |
| A 가 참석을 바꾸면 B 의 하객 수 · 식대도 갱신 | 4ms · ₩300,000 → ₩250,000 |
| A 가 결제 완료 → B 의 예산 · 다가오는 결제 | 2–8ms, 목록에서도 사라짐 |
| 서로 **다른 칸**을 동시에 고칠 때 | 둘 다 살아남음(제목 · 메모 각각 보존) |
| 같은 칸을 동시에 고칠 때 | 나중 것이 이김 + 진 쪽에 안내 |
| 같은 이벤트가 두 번 와도 | 한 건만 남음 |
| 최근 활동의 '누가' | 신랑 · 신부 각각 정확히 기록 |
| 식대 계산 (150명 · 300명) | 화면 = 손으로 센 값과 일치 |
| 스크롤 (문서 높이 26,692px) | 50ms 넘는 프레임 0개 |

## 일부러 만들지 않은 것

- 버전 관리 · 병합 · 편집 잠금 — 두 사람이 쓰는 앱에 과하다. **나중 것이 이기고, 진 쪽에 알려준다**가 규칙이다.
- 하객 목록 가상 스크롤 — 300명에서 첫 화면 0.8초, 스크롤 끊김 0이다. 필요해지면 그때 만든다.
