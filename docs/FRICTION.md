# 마찰 감사 (Friction Audit)

> 느낌이 아니라 **센 숫자**로 관리한다.
> `BASE=http://localhost:3001 node qa/audit.mjs` 가 실제로 화면을 조작하면서
> 사람이 몇 번 손대야 하는지를 세고, 목표를 넘으면 실패로 처리한다.
>
> 측정 환경: 390×844 (실제 주 사용 기기), 로컬 저장 모드.

## 왜 자동으로 세는가

"편해졌나?" 는 물어볼 때마다 답이 달라진다. 클릭 수는 안 그렇다.
기능을 더하다 보면 조용히 한 단계가 늘어나는데, 사람은 그걸 잘 못 느낀다.
그래서 열여섯 개 시나리오의 손동작 수를 매번 세고, 늘어나면 CI 에서 걸리게 했다.

## 이번 감사에서 실제로 찾아 고친 것

### 1. 방금 추가한 비용 항목이 사라진다 (가장 나빴던 것)

금액 없는 예산 항목은 접어 두는 게 맞다 — 이관된 빈 항목이 21개나 있다.
그런데 새 비용을 추가하면 금액이 0이라 **곧바로 그 접힘 속으로 사라졌다.**
사용자에게는 "저장이 안 됐나?" 가 된다.

고친 방법: 이 탭에서 직접 만든 것은 접힘 규칙을 건너뛴다 (`src/lib/fresh.ts`).

> 처음엔 '만든 시각이 최근인가' 로 판단했는데 틀렸다. 원본 이관 데이터도
> 처음 켠 순간 전부 '방금' 이 되어 버려서(`buildMigratedData` 가 지금 시각을 찍는다)
> 접힘이 통째로 풀렸다. 시계를 보지 않고 실제로 `add()` 한 id 만 기억하도록 바꿨다.
> sessionStorage 에 둬서 새로고침해도 남고 탭을 닫으면 사라진다.

### 2. 금액 수정이 시트 안의 시트였다 (5번 → 3번)

목록 → 상세 시트 → 금액 버튼 → **또 시트** → 숫자 → 닫기 → 닫기.
결혼 준비 중 가장 자주 하는 일 치고 너무 멀었다.

고친 방법: 목록 줄의 **예상 / 실제 금액을 각각 직접 누르면** 숫자패드가 바로 뜬다.
상세 시트를 열 필요가 없다.

### 3. 식장 화면이 하객 명단을 안 쓰고 있었다 (데이터 정합성)

식장에 손으로 적어 둔 '예상 인원' 으로 식대를 계산하고 있었다.
앱이 이미 하객 명단에서 진짜 인원을 알고 있는데도.
같은 숫자를 두 군데서 관리하면 반드시 어긋난다.

고친 방법: `computeMealEstimate()` 한 곳에서만 센다. 명단이 있으면 명단이 정답,
비었을 때만 적어 둔 값을 쓴다.

### 4. 계약 식장 이름을 눌러도 아무 일이 없었다

고치려는 사람은 제목을 먼저 누른다. 이름도 상세를 열도록 했다.

## 데이터 정확성 (13가지 전부 통과)

같은 숫자가 화면마다 같은지를 **원장부에서 직접 센 값과 비교**한다.
앱의 계산을 앱의 계산과 비교하면 둘 다 틀려도 통과하므로, 기준은 늘 원본 데이터다.

- 홈 '사용 금액' = 실제금액 합계
- 예산 '총 실제 비용' = 실제금액 합계 / '총 결제 금액' = 결제완료 합계
- **홈과 예산이 같은 '사용 금액'** 을 보여주는가
- 하객 '예상 총 인원' = 불참 뺀 (본인 + 동반)
- 신랑 + 신부 + 공통 = 전체 (겹쳐 세지 않음)
- 참석확정 ≤ 예상 인원
- 홈 '준비 진행률' = 완료 / 전체
- D-Day, 결혼식 날짜, 음수 금액 · 음수 인원 · 1900년대 날짜 없음

## 목표를 정할 때 쓴 기준

- **확인만 하는 일은 0번.** 홈을 열면 이미 보여야 한다.
- **자주 하는 상태 변경은 1번.** 완료 · 참석 · 청첩장 · 결제.
- **추가는 2번** (목록에서 제목만) 또는 **4~5번** (FAB 으로 자세히).
- **수정은 3번 이내.**
